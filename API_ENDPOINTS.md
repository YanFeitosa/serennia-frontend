# API da Serenna – Endpoints Propostos\n\n> Estrutura de API REST pensada para integrar o front atual. Foca em clareza de domínio e no que a UI realmente precisa. IDs são strings (UUID ou similares). Datas são ISO 8601 (`string`).\n\n---\n\n## 1. Autenticação e sessão\n\n### POST /auth/login\n- **Função**: autenticar usuário por e-mail/senha.\n- **Entrada**: `{ email: string, password: string }`\n- **Saída**: `{ user: User, accessToken: string, refreshToken?: string }`\n\n### POST /auth/logout\n- **Função**: invalidar sessão/token atual.\n- **Entrada**: header `Authorization: Bearer <token>`.\n- **Saída**: 204 (sem corpo).\n\n### POST /auth/refresh\n- **Função**: renovar `accessToken` com base no `refreshToken`.\n- **Entrada**: `{ refreshToken: string }`\n- **Saída**: `{ accessToken: string }`\n\n### GET /auth/me\n- **Função**: retornar dados do usuário logado (para popular Sidebar, etc.).\n- **Saída**: `User`.\n\n---\n\n## 2. Usuários e Colaboradores\n\n### GET /users/me\n- **Função**: alias de `/auth/me`, usado para garantir tipagem única de `User`.\n\n### GET /collaborators\n- **Função**: listar colaboradores (para tela de Colaboradores, agenda, comissões).\n- **Query** (opcional): `status`, `role`, `search`.\n- **Saída**: `Collaborator[]`.\n\n### GET /collaborators/:id\n- **Função**: detalhes de um colaborador (Perfil do Colaborador).\n- **Saída**: `Collaborator` + (opcionalmente) métricas agregadas (ex.: faturamento, comissões).\n\n### POST /collaborators\n- **Função**: criar colaborador.\n- **Entrada**: campos de `Collaborator` exceto `id`, `createdAt`, `updatedAt`.\n- **Saída**: `Collaborator`.\n\n### PUT /collaborators/:id\n- **Função**: atualizar colaborador (nome, role, status, comissão, etc.).\n- **Saída**: `Collaborator`.\n\n### PATCH /collaborators/:id/status\n- **Função**: ativar/inativar colaborador rapidamente.\n- **Entrada**: `{ status: 'active' | 'inactive' }`.\n\n---\n\n## 3. Clientes\n\n### GET /clients\n- **Função**: listar clientes (tela de Clientes).\n- **Query** (opcional): `search` (nome ou telefone), `tag`, `page`, `pageSize`.\n- **Saída**: lista paginada de `Client`.\n\n### GET /clients/:id\n- **Função**: detalhes de cliente (Perfil do Cliente).\n- **Saída**:\n  - `client: Client`\n  - `lastOrders?: Order[]` (últimas comandas para timeline do perfil).\n\n### POST /clients\n- **Função**: criar cliente (ClienteForm).\n- **Entrada**: campos de `Client` exceto `id`, `createdAt`, `updatedAt`.\n- **Saída**: `Client`.\n\n### PUT /clients/:id\n- **Função**: atualizar dados do cliente.\n- **Saída**: `Client`.\n\n### GET /clients/:id/orders\n- **Função**: listar comandas de um cliente (histórico no perfil).\n- **Saída**: `Order[]`.\n\n---\n\n## 4. Catálogo – Serviços e Produtos\n\n### GET /services\n- **Função**: listar serviços (tela de Serviços, agendamento, totem).\n- **Query** (opcional): `search`, `category`, `isActive`.\n- **Saída**: `Service[]`.\n\n### GET /services/:id\n- **Função**: detalhar um serviço para edição.\n- **Saída**: `Service`.\n\n### POST /services\n- **Função**: criar serviço.\n- **Entrada**: campos de `Service` exceto `id`, `createdAt`, `updatedAt`.\n\n### PUT /services/:id\n- **Função**: atualizar serviço.\n\n### PATCH /services/:id/status\n- **Função**: ativar/inativar serviço (campo `isActive`).\n\n---\n\n### GET /products\n- **Função**: listar produtos (tela de Produtos, seleção em comanda).\n- **Query** (opcional): `search`, `category`, `isActive`.\n- **Saída**: `Product[]`.\n\n### GET /products/:id\n- **Função**: detalhar produto.\n- **Saída**: `Product`.\n\n### POST /products\n- **Função**: criar produto.\n- **Entrada**: campos de `Product` exceto `id`, `createdAt`, `updatedAt`.\n\n### PUT /products/:id\n- **Função**: atualizar produto (nome, preço, estoque, etc.).\n\n### PATCH /products/:id/status\n- **Função**: ativar/inativar produto.\n\n---\n\n## 5. Agenda (Appointments)\n\n### GET /appointments\n- **Função**: listar agendamentos para exibir na agenda principal.\n- **Query**: `from`, `to` (intervalo de datas), `collaboratorId?`, `status?`.\n- **Saída**: `Appointment[]`.\n\n### GET /appointments/:id\n- **Função**: obter detalhes de um agendamento específico (edição).\n- **Saída**: `Appointment`.\n\n### POST /appointments\n- **Função**: criar agendamento.\n- **Entrada**: `clientId`, `collaboratorId`, `serviceIds`, `start`, `end`, `origin`, `notes?`.\n- **Saída**: `Appointment`.\n\n### PUT /appointments/:id\n- **Função**: atualizar agendamento (reagendar, trocar profissional, etc.).\n\n### PATCH /appointments/:id/status\n- **Função**: alterar status (confirmar, cancelar, no_show, completed).\n- **Entrada**: `{ status: AppointmentStatus }`.\n\n---\n\n## 6. Comandas / Orders\n\n### GET /orders\n- **Função**: listar comandas (tela de Comandas, filtros open/closed/paid, busca).\n- **Query**: `status?`, `clientId?`, `search?`, `from?`, `to?`.\n- **Saída**: `Order[]` (sem itens detalhados ou com `items` completos, conforme necessidade).\n\n### GET /orders/:id\n- **Função**: detalhes de uma comanda (itens, valores, cliente).\n- **Saída**: `Order` + (opcional) `client: Client`.\n\n### POST /orders\n- **Função**: abrir nova comanda para um cliente (fluxo "Nova Comanda").\n- **Entrada**: `{ clientId: string, appointmentId?: string }`.\n- **Saída**: `Order`.\n\n### PATCH /orders/:id\n- **Função**: atualizar metadados da comanda (ex.: `status`, `discount`).\n- **Entrada**: subset de `{ status, discount }`.\n\n### POST /orders/:id/items\n- **Função**: adicionar item (serviço ou produto) a uma comanda (usado em ComandaDetails).\n- **Entrada**: `{ type: 'service' | 'product', serviceId?: string, productId?: string, collaboratorId?: string, quantity?: number }`.\n- **Saída**: `Order` atualizado.\n\n### DELETE /orders/:id/items/:itemId\n- **Função**: remover item da comanda.\n- **Saída**: `Order` atualizado.\n\n### POST /orders/:id/close\n- **Função**: fechar comanda (status `closed`), normalmente antes de pagamento.\n- **Saída**: `Order` atualizado.\n\n### POST /orders/:id/reopen\n- **Função**: reabrir comanda fechada (se sua regra de negócio permitir).\n\n---\n\n## 7. Pagamentos\n\n### GET /orders/:id/payments\n- **Função**: listar pagamentos associados a uma comanda (para histórico).\n- **Saída**: `Payment[]`.\n\n### POST /orders/:id/payments\n- **Função**: registrar um pagamento (tela de PagamentoComanda).\n- **Entrada**: `{ method: PaymentMethod, amount: number }`.\n- **Saída**: `{ order: Order, payment: Payment }`.\n\n### POST /payments/:id/refund\n- **Função**: registrar estorno/reversão (opcional, para futuro).\n\n---\n\n## 8. Financeiro\n\n> A tela de Financeiro hoje consome basicamente comandas pagas e calcula agregados no front. A API pode oferecer endpoints agregados para simplificar.\n\n### GET /finance/orders\n- **Função**: listar comandas pagas no intervalo (para tabela e cards).\n- **Query**: `from`, `to`, `clientId?`, `collaboratorId?`.\n- **Saída**: `Order[]` (apenas `status = 'paid'`).\n\n### GET /finance/summary\n- **Função**: retornar resumo numérico (cards superiores).\n- **Query**: `from`, `to`.\n- **Saída** (exemplo):\n  ```ts\n  {
    totalRevenue: number;      // soma de finalValue das paid
    totalCommission: number;   // soma de CommissionRecord ou de items
    estimatedProfit: number;   // totalRevenue - totalCommission - (opcional: custo produtos)
  }
  ```\n\n### GET /finance/chart\n- **Função**: retornar dados agregados para o gráfico (diário/semanal/mensal/anual).\n- **Query**: `from`, `to`, `resolution=day|week|month|year`.\n- **Saída**: array de pontos `{ name: string, faturamento: number, comissao: number }`.\n\n### GET /finance/commissions\n- **Função**: listar registros de comissão por colaborador e período (futuro módulo de comissão).\n- **Query**: `from`, `to`, `collaboratorId?`, `paid?`.\n- **Saída**: `CommissionRecord[]`.\n\n---\n\n## 9. Auditoria\n\n### GET /audit-logs\n- **Função**: listar logs de auditoria (tela de Auditoria).\n- **Query**: `from?`, `to?`, `userId?`, `tableName?`, `action?`.\n- **Saída**: `AuditLog[]`.\n\n### GET /audit-logs/:id\n- **Função**: detalhes de um log específico (se precisar expandir no futuro).\n\n---\n\n## 10. Notificações\n\n### GET /notifications\n- **Função**: listar notificações do usuário logado (tela de Notificações, badge no menu).\n- **Query**: `unreadOnly?`.\n- **Saída**: `Notification[]`.\n\n### PATCH /notifications/:id/read\n- **Função**: marcar notificação como lida.\n- **Entrada**: `{ read: boolean }`.\n\n### POST /notifications\n- **Função**: criar uma notificação (ex.: ações automáticas do sistema).\n- **Entrada**: `Notification` parcial (sem `id`, `createdAt`).\n\n---\n\n## 11. Configurações / Aparência\n\n> Parte do que hoje está apenas no `localStorage` (nome da plataforma, tema) pode ser centralizado no backend.\n\n### GET /settings/appearance\n- **Função**: obter configurações de aparência do salão (nome exibido, tema padrão etc.).\n- **Saída** (exemplo): `{ platformName: string, theme: 'light' | 'dark' }`.\n\n### PUT /settings/appearance\n- **Função**: atualizar configurações de aparência.\n- **Entrada**: `{ platformName?: string, theme?: 'light' | 'dark' }`.\n\n---\n\n## 12. Totem (autoatendimento)\n\nAs telas de totem usam basicamente serviços, identificação do cliente e criação de agendamento/entrada.\n\n### GET /totem/services\n- **Função**: listar serviços disponíveis no totem (pode ser subset de `/services`).\n\n### POST /totem/checkin\n- **Função**: registrar um novo atendimento vindo do totem.\n- **Entrada** (exemplo): `{ clientId?: string, phone?: string, name?: string, serviceIds: string[] }`.\n- **Saída**: `{ appointment: Appointment, order?: Order }` conforme seu fluxo.\n\n---\n\n## 13. Considerações finais\n\n- Os endpoints acima cobrem todas as telas e ações do front atual: login, menu lateral por role, agenda, clientes, comandas, serviços, produtos, financeiro, auditoria e notificações.\n- Alguns agregados (Financeiro, Comissões) podem inicialmente ser calculados no backend reaproveitando a mesma estrutura de `Order`/`OrderItem` definida nas tipagens.\n- À medida que o backend evoluir, dá para especializar mais as respostas (por exemplo, endpoints específicos para dashboards) sem quebrar o front, desde que os campos principais (`id`, `status`, `finalValue`, etc.) sejam preservados.\n
